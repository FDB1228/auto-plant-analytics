# 5. Платформа данных

## Слои

| Слой | Схема | Что хранит | Как обновляется |
|---|---|---|---|
| Источник: MES | `plant` | нормализованная операционная БД (34 таблицы) | `pipeline/source_loader.py` - UPSERT состояния на дату |
| Источники: ERP, дилерский портал | файлы `data/landing/...` | CSV плана (cp1251, `;`, версии) и JSON гарантийных заявок | файлы «появляются» по дате публикации |
| RAW | `raw` | файлы как есть (все поля - `text`) + `_source_file`, `_row_number`, `_loaded_at` | `pipeline/ingest.py`, идемпотентно |
| Staging | `staging` | очистка и типизация, 1:1 с источниками (views) | dbt |
| Intermediate | `intermediate` | бизнес-логика: актуальная версия плана, итоговое состояние заявки, состав бригады на каждый день, качество по изделию | dbt (tables) |
| Snapshots | `snapshots` | SCD2-история сотрудников | `dbt snapshot` (strategy `check`) |
| Marts | `marts` | звезда (`dim_*`, `fct_*`) и витрины под BI (`mart_*`) | dbt; два факта - инкрементальные |
| DQ | `dq` | строки, не прошедшие тесты (`store_failures`) | dbt test |

## Загрузка внешних файлов (`ingest`)

- **Идемпотентность:** каждый загруженный файл записывается в `raw.load_log` (имя + sha256). Повторный запуск пропускает загруженное; изменившийся после загрузки файл не перезаписывается молча, а выводится предупреждение.
- **Атомарность:** строки файла и запись в журнале - в одной транзакции; сбой посреди файла не оставляет половину данных.
- **Без интерпретации:** в RAW всё хранится текстом, JSON - целиком в `payload jsonb`. Ошибки разбора дат и сумм не блокируют загрузку, а ловятся тестами staging.

### Что «грязного» в данных портала и где это чинится

| Проблема | Пример | Решение (`stg_dealer__warranty_claims`, `int_warranty_claims_current`) |
|---|---|---|
| VIN в разном регистре и с пробелами | `x9psksd10sk001234`, `X9P SKSD10 SK001234` | `upper(regexp_replace(vin, '\s', '', 'g'))` + тест длины 17 |
| Даты в двух форматах | `2025-03-14` и `14.03.2025` | разбор по регулярному выражению |
| Суммы строкой в русском формате | `"45 300,00"` | удаление пробелов (вкл. неразрывные), замена запятой |
| Полные дубли записей | повторная отправка | `DISTINCT ON` по (заявка, статус, время) |
| Несколько событий одной заявки | `submitted` → `approved` | последнее событие по `record_updated_at`, дата подачи - из первого |
| Пустой код дефекта | `null` | `origin_area = 'UNKNOWN'` в факте |
| Время без часового пояса | `2025-03-14T12:30:00` | явная интерпретация как `Europe/Moscow` |

## Инкрементальная загрузка

`fct_operations` и `fct_tests` - инкрементальные модели (`unique_key`, delete+insert). Окно пересчёта - 3 дня от последней загруженной записи. Отдельно обрабатываются **поздно приходящие факты**: дефект, допущенный на сварке во вторник, может быть найден на испытаниях в четверг, и флаг `caused_defect` у операции вторника должен измениться задним числом. Поэтому в инкремент, помимо новых операций, попадают операции, на которые ссылаются недавно обнаруженные дефекты:

```sql
where o.finished_at > (select since from watermark)
   or o.operation_id in (select origin_operation_id from stg_plant__defects
                         where detected_at > (select since from watermark))
```

Корректность проверена сверкой: после двух инкрементальных прогонов `fct_operations` совпадает с полным пересчётом (0 расхождений по `caused_defect` и составу бригады).

## Демонстрация «живой» работы

Генератор создаёт полную историю, а `source_loader` собирает из неё состояние MES **на дату**: незавершённые операции ещё не видны, дата увольнения неизвестна, пока не наступила, статус изделия соответствует дате. `make pipeline` делает два прогона:

| Прогон | Что происходит |
|---|---|
| на 30.06.2026 | первичная загрузка: 19.4 тыс. изделий, 103 файла внешних систем, полная сборка хранилища |
| на 30.09.2026 | +2.8 тыс. изделий, 274 изделия меняют статус (UPSERT обновляет только изменённые строки - `updated_at` честный), +16 файлов; инкрементальные модели дозагружают ~15 тыс. операций; снапшот фиксирует ~55 новых версий сотрудников (повышение разряда, увольнения) |

## Контроль качества данных (72 теста)

| Тип | Примеры |
|---|---|
| Ключи | `unique` + `not_null` для всех первичных ключей фактов и измерений; уникальность составных ключей витрин |
| Ссылочная целостность | `relationships` факта операций к измерению бригад |
| Допустимые значения | статусы изделий, заявок, точки обнаружения дефекта, смены |
| Диапазоны | длительность операции 1-3000 мин, доли 0-1, план 0-2000 шт. |
| Бизнес-правила (singular) | операции внутри жизненного цикла изделия; бригада существует на дату работ; у операции известен состав бригады; заявка не раньше отгрузки; ровно одна актуальная версия SCD2 без пересечений |
| Сверки | число принятых изделий в дневной витрине = числу в `fct_units` |
| Мониторинг источников (`warn`) | доля заявок с VIN, не найденным в MES, ≤ 1%; аномалии план-факта < 70% или > 130%; свежесть источников (`dbt source freshness`) |

## Оркестрация и CI

- **Локально:** `python -m pipeline.run daily --as-of YYYY-MM-DD` - load-source → ingest → dbt build; `make pipeline` - демо из двух прогонов.
- **Airflow:** `orchestration/airflow/dags/plant_dwh_dag.py` - те же шаги отдельными задачами с ретраями, плюс `dbt source freshness` и выгрузка для BI; расписание - будни 06:00, после закрытия ночной смены; дата состояния - логическая дата запуска (`{{ ds }}`), поэтому возможен backfill.
- **CI (GitHub Actions):** на каждый push поднимается PostgreSQL 16, прогоняются pytest, генерация уменьшенного набора (15% объёма) и полный пайплайн с тестами dbt.

## Производительность

Полный цикл на ноутбуке: генерация ~5 с, загрузка MES ~10 с, dbt build (51 модель + 72 теста) ~5 с. Индексы OLTP рассчитаны на типовые запросы (по времени, бригаде, изделию) и на инкрементальную выгрузку (`updated_at`, `finished_at`); в инкрементальных моделях - индексы по `work_date`, `(brigade_id, work_date)`, `unit_id`.
